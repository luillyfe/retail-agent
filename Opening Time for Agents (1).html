    • Act 1 · The point of sale as Go services run it

    Smart tablets, stateless services

    The tablet holds state. The services don't. That split is what makes both of them scale.

  • Start with the tablet: it talks to hardware, keeps the active cart in memory, and persists a local datastore so it can sell offline.
  • → The services: stateless, behind a load balancer, cache outside the pod. Any instance can serve any request.
  • → Tracing ties it together. → The split.
  • Expert detail: in-memory alone would lose a sale on a reboot; that's why the outbox is persisted.
    • The non-negotiables

    Scan, total, pay, refund. Every time, in milliseconds.

    Stateless and horizontal

    Add instances at opening time, remove them at night. No sticky sessions.

    Low latency

    Goroutines for fan-out, connection pools and timeouts tuned per dependency.

    Fault tolerant

    Retries with backoff, and idempotency keys so a retry never charges twice.

    Strict security

    Tokenized payments, least privilege between services, every call traced.

    Predictable is the feature. Agents don't replace any of this.

  • This is where you say the line from your notes: traditional architectures are not going anywhere.
  • Idempotency keys are the detail experts listen for: retries are only safe when a step can run twice.
    • Checkout spans five services

    Checkout is a saga, not a distributed lock

    Each step is a local transaction in one service. No step holds a lock while it waits for the next. If one fails, the earlier steps are undone by compensations, in reverse order.

    StepCompensation
    1Reserve inventoryRelease inventory
    2Redeem loyalty pointsRestore points
    3Authorize payment Void the authorization
    4Create the orderCancel the order
    5Print and sync the receipt(last step, nothing after it)

    The price: no isolation. Other services can see the in-between states, so the system is eventually consistent.

  • → all steps succeed. → payment fails at step 3. → compensations run for steps 2 and 1, and the trade-off appears.
  • Precision: a saga is an alternative to a two-phase commit, not an implementation of one.
    • The saga in GoCompensations must outlive the request that started them.
    
        
    A production saga also persists its progress, so a crash mid-checkout resumes or compensates on restart.
    
      
    
      
    
        
  • Point at context.WithoutCancel: if the guest walks away and the request is canceled, the refund must still happen.
    • 
        
  • Steps must be idempotent, because compensations and retries can run more than once.

    When the network drops at 9:05
    
        
    Real-time when online, reconciled when not
    
        
    
          
    
            
    Online
    
            
    Inventory and loyalty sync in real time
    
            
    Every sale updates stock and points as it happens. Other registers see it within seconds.
    
          
    
          
    
            
    Offline
    
            
    The tablet keeps selling from its local datastore
    
            
    Sales go to the outbox under stricter rules: an offline sale limit, no point redemptions, refunds wait.
    
          
    
          
    
            
    Back online
    
            
    The outbox replays, idempotently
    
            
    Each event carries its idempotency key, so a replay can't double-count a sale. Conflicts go to a person.
    
          
    
        
    
      
    
      
    
        
  • This resolves the tension between "offline-first" and "real-time sync": real-time is a property of the online mode only.
    • 
        
  • The offline rules (sale limit, no redemptions, deferred refunds) are my proposal; tune them per business.
    • 
        
  • Offline card payments depend on the payment provider supporting store-and-forward.

  • This is the thesis of the whole talk. Read the second line slowly.
    • 
      
    
    
    

    
    
      
    
        
    More than one agent, each with less power
    
        
    Two agents, and two things that are not agents
    
        
    
          
    
            
    Concierge
    
            Guest-facing · simple tasks on the tablet, multi-step in the agent service
            
    • Can search the catalog, check stock, build a cart
    • Can propose a cart with points to redeem
    
            
    • Cannot set a price, take a payment or issue a refund
    
            
    catalog.searchinventory.checkloyalty.balancecart.propose
    
          
    
          
    
            
    Associate
    
            Staff-facing, for the cashier and shop lead
            
    • Can look up orders, stock in other shops, exchanges
    • Can propose a refund, with a reason
    
            
    • Cannot execute a refund without a staff approval
    
            
    order.lookupinventory.queryrefund.propose
    
          
    
          
    
            
    Not agents
    
            Deterministic Go services
            
    • Rules service validates every proposal
    • Saga orchestrator executes what passed
    • Audit log records all of it
    
          
    
        
    
      
    
      
    
        
  • Why two agents: different users, different tools, different blast radius. A guest-facing agent should never have refund tools.
    • 
        
  • The third card is the point: the parts that touch money are not agents.
    • 
      
    
    
    

    
    
      
    
        
    Where the agent loop runs
    
        
    Simple on the tablet, multi-step in Go
    
        
    
        
        
    
        
    Two loops, one contract: both end in a cart proposal checked by the same rules.
    
      
    
      
    
        
  • Start with the tablet: the router, redaction, an on-device loop and a local copy of the rules. That's enough to help a guest offline.
    • 
        
  • → The backend: a stateless Go agent service with the cloud model, next to the services it calls as tools.
    • 
        
  • → The contract: whichever loop ran, its proposal goes to the same rules before anything is sold.
    • 
        
  • The honest cost: two loop implementations, one in the tablet app's language and one in Go, to keep in sync. Shared tool schemas and the shared proposal contract keep them aligned.
    • 
      
    
    
    

    
    
      
    
        
    Two models, one router
    
        
    On the tablet when it can, in the cloud when it must
    
        
    
          
    
            
    On-device model
    
            
    
              
    Good at
    parsing intent, simple catalog search, short answers
    
              
    Latency
    a few hundred milliseconds
    
              
    Offline
    yes, the only model available
    
              
    Data
    never leaves the tablet
    
            
    
          
    
          
    
            
    Cloud model
    
            
    
              
    Good at
    multi-step flows: loyalty, bundles, exchanges
    
              
    Latency
    one to a few seconds
    
              
    Offline
    no; the router falls back
    
              
    Data
    redacted context and tokens only
    
            
    
          
    
        
    
        
    
      
    
      
    
        
  • The router is deterministic code, not a model. It runs once per request, outside any loop, so a run never switches models halfway.
    • 
        
  • Both loops implement the same Runner interface: Run(ctx, task) returns a CartProposal.
    • 
        
  • If the agent-service call fails mid-request, the tablet falls back to the on-device loop and tells the guest what it can't do offline.
    • 
        
  • Latencies are illustrative; measure your own models on your own hardware.
    • 
      
    
    
    

    
    
      
    
        
    The agent service · backendStateless GoA model, a loop and an allow-list of tools, inside a budget.
    
        
    
      
    
      
    
        
  • This is the backend half of option C. Point at the three parts: the model (line 4), the tools (line 5), the loop (the for statement).
    • 
        
  • The model is chosen once, before the loop, by the tablet's router. Nothing inside the loop can switch it.
    • 
        
  • No redaction here: the tablet redacted the working memory before sending it. No state either: everything the run needs arrives in the request.
    • 
        
  • The loop never executes anything with money: it ends by returning a CartProposal, which goes to the rules service.
    • 
        
  • Tool allow-list is the permission system: if a tool isn't in the map, the agent can't call it. The budget caps time and steps so a confused model can't hold up the line.
    • 
      
    
    
    

    
    
      
    
        
    A memory layer for each part of the system
    
        
    Four kinds of agent memory, and two things that aren't
    
        
    
          
    MemoryTypeLives inLastsAgents canRule
    
          
    Workingthe conversation right nowShort-term · in contexttablet RAM, sent with each agent-service requestone sessionread and writeredacted on entry; wiped at checkout
    
          
    Store knowledgecatalog, prices, policiesSemantic · retrievedlocal datastore, synceduntil the next versionread through toolsversioned, so every answer names its snapshot
    
          
    Guest memorypurchase history, preferencesEpisodic → profile · retrievedcloud, keyed by loyalty tokena retention periodread one summary per sessionloyalty opt-in only; no card data, ever
    
          
    Instructionssystem prompt, tool specs, router policyProcedural · in codecode and config, deployeduntil the next releasefollow it, never change itreviewed like code; improved offline from the decision log
    
          
    Cart stateitems, sizes, pointsNot agent memory · state it observestablet cart store, persisteduntil the sale syncsread; change only by proposalowned by the POS, never by the model
    
          
    Decision logwhat was proposed and whyNot agent memory · a record of itoutbox, then cloudper audit policynothing at runtimeappend-only; written by Go, not by the agent
    
        
    
        
    Only working memory sits in the context. The rest is pulled through tools, or never read at all.
    
      
    
      
    
        
  • Four rows of agent memory first: short-term, semantic, episodic, procedural. Then the two that only look like memory.
    • 
        
  • Pull-on-read: store knowledge and guest memory reach the model through tools, so the context stays small and private.
    • 
        
  • Procedural memory is the answer to "where do the instructions live?": in code and config, versioned and deployed.
    • 
        
  • The cart is the environment the agent acts on; the POS owns it. The decision log is a record of the agent, not memory for it: an agent that read its own log could learn from a bad decision.
    • 
        
  • Learning happens offline: people review the decision log and promote good patterns into procedural memory.
    • 
        
  • Guest memory is personal data: consent, retention and minimization apply even though PCI doesn't.
    • 
      
    
    
    

    
    
      
    
        
    The contractThe agent proposes SKUs and quantities. It never sends a price.
    
        
    
      
    
      
    
        
  • Prices come from the catalog inside Validate, so a model can't invent one.
    • 
        
  • A rejection goes back to the agent as an observation, the same way a failed tool call does.
    • 
        
  • The guest confirms on screen before the saga runs. That's the human in the loop for money.

    Act 3 · What agents bring with them
    
        
    Three new problems at the register
    
        
    
          
    Reasoning latency
    A model thinks in seconds. A checkout line moves in milliseconds.
    
          
    Privacy and PCI
    A conversation can contain anything, including a card number read out loud.
    
          
    Autonomy and explainability
    "The model decided" is not an answer an auditor accepts.
    
        
    
        
    The controls: guardrails, external rule validation and structured audit logs.
    
      
    
      
  • Name the three problems, then one scene each.
    • 
    
    

    
    
      
    
        
    Problem 1 · Latency
    
        
    The agent never sits on the scan path
    
        
    
          
    
            
    Scan path, pure Go scan → price → total
    
            
    
          
    
          
    
            
    Agent path, on-device intent → search → answer
    
            
    intenttoolsanswer
    
          
    
          
    
            
    Agent path, cloud multi-step reasoning
    
            
    intenttoolscloud reasoning
    
          
    
          
    00.5 s1 s1.5 s2 s
    
        
    
        
    Illustrative timings. The scan path runs in tens of milliseconds and never waits for a model.
    
      
    
      
    
        
  • The register keeps scanning while the agent thinks. Agents help before checkout, not inside it.
    • 
        
  • Budgets from the harness cap the agent path: past the limit, the agent says it couldn't finish.
    • 
      
    
    
    

    
    
      
    
        
    Problem 2 · Privacy and PCI
    
        
    The model never sees card data
    
        
    
        
        
    
        
    Keeping models outside the payment boundary keeps them out of PCI scope.
    
      
    
      
    
        
  • Guests will read card numbers out loud. The redaction step runs in Go before any model call, on-device or cloud.
    • 
        
  • Guest memory carries purchase history, which is still personal data: consent and retention apply.
    • 
      
    
    
    

    
    
      
    
        
    Problem 3 · Autonomy
    
        
    Agents stop one rung below the money
    
        
    
          
    1Answer and suggest"Two shirts under $30 are in stock here." No approval needed.
    
          
    2Propose structured actionsA cart proposal, a refund proposal. Always passed to the rules service.
    
          
    3Execute after rules and a humanThe guest confirms a sale, staff approve a refund, then the saga runs.
    
          
    4Execute on its ownNot allowed for anything that moves money or stock.
    
        
    
        
    Guardrails sit at every rung: tool allow-lists, budgets, redaction, and rules the model can't argue with.
    
      
    
      
    
        
  • The ladder is the answer to "stricter controls on autonomy": you choose the rung per action, and money is capped at 3.
    • 
      
    
    
    

    
    
      
    
        
    Explainable decision logsStructured, append-only, written by Go. One record per decision, joined to the trace.
    
        
    
      
    
      
    
        
  • "Why did the register give that discount?" is answered by this record, not by asking the model again.
    • 
        
  • The trace ID joins the decision to every service call in distributed tracing.

      Question 1 of 6
      Saga
      
        
      Compared with a two-phase commit, what does a saga give up?
      
        
      
          
      ADurability
      
          
      BIsolation
      
          
      CAvailability
      
          
      DRetries
      
        
      
        
      B
      Each local transaction commits on its own, so other services can see the in-between states. That's why the system is eventually consistent.
      
      
      
      
    • Availability is the tempting answer; sagas actually improve it by avoiding long-lived locks.
      • 
    
      

    
      
      
      
        
      Question 2 of 6
      Saga
      
        
      Payment was authorized, then creating the order fails. What's the compensation for the payment step?
      
        
      
          
      ARetry the order forever
      
          
      BVoid the authorization
      
          
      CAsk the model what to do
      
          
      DDelete the decision log entry
      
        
      
        
      B
      Each step carries its own undo. Compensations run in reverse order, in Go, and they're logged like everything else.
      
      
      
      
    • If someone says C, that's the whole talk in one wrong answer.
      • 
    
      

    
      
      
      
        
      Question 3 of 6
      PCI
      
        
      What does the agent see when the guest pays?
      
        
      
          
      AThe encrypted card number
      
          
      BThe last four digits and the expiry date
      
          
      CA payment token reference
      
          
      DThe full card number, but only on-device
      
        
      
        
      C
      Card data stays inside the payment boundary. Agents handle a token at most, which keeps them out of PCI scope.
      
      
      
      
    • D is the trap: "on-device" doesn't make card data safe to put in a model.

      Question 4 of 6
      Memory
      
        
      Where does the guest's current cart live?
      
        
      
          
      AIn the model's context window
      
          
      BIn the tablet's cart store, read by the agent through a tool
      
          
      CIn the guest's long-term memory
      
          
      DIn the decision log

      Question 5 of 6
      Go
      
        
      The outbox replays sales after the network comes back. What makes that safe?
      
        
      
          
      AIdempotency keys on every event
      
          
      BHolding a lock until the replay finishes
